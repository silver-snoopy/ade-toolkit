ADE Development Pipeline — Deep Study (Phases 0–6)

A narrowed, maximum-rigor study of ADE's development pipeline only — Intent → Research → Plan → Design-Check → Implement → Quality-Gate → Review — the path that turns an intent into reviewed, working code, before ship/docs/compound. Each phase is read from the real v3 SKILL.md sources and benchmarked against the agentic-SDLC field through five lenses, with one question as the spine: what are the strengths, where must ADE improve, and what is missing entirely?

Phases in scope  0–6 Field corpus  16 systems (prior re-benchmark) Targeted re-verify agents  4 Primary source  v3 generated tree Date  2026-06-21
Bottom line

The ADE development pipeline is field-leading on the hardest-to-fake dimensions of the inner loop — research-and-verification rigor (a spec-blind Chain-of-Verification no competitor matches), hook-enforced author-separated TDD (the only live EXIT=2 mixed-commit block in the field), blast-radius phase-masking routing, an executable design-contract gate, and deterministic circuit breakers on every loop. The weaknesses are concentrated and fixable: independent plan validation runs only on the architecture tier (the median change grades its own plan); the design-stub gate has no independent reviewer; the fixer loop uses a bare integer cap where leaders use stall-detection; and review is single-model. The one true regression remains G6 — live, evidence-based verification was removed (as a cost of the G5 stack-agnosticism win) and replaced by a test-coverage gate, leaving ADE alone among strong systems with zero runtime proof. The genuinely missing capabilities are design-time threat modeling and forced, falsifiable NFR/capacity targets — both of which would extend, not rebuild, ADE's strongest phase.

00Scope & method

In scope — the development pipeline up to (not including) compound: Phase 0 Intent + routing, Phase 1 Research (R1–R5), Phase 2 Plan, Phase 3 Design-Check, Phase 4 Implement, Phase 5 Quality-Gate, Phase 6 Review. The test for inclusion: "does this step turn an intent into reviewed, working code?"

Out of scope — the compound loop (Phase 9 retro / compounder / docs/learnings/ as a compounding mechanism), Phase 7 Docs, Phase 8 Ship, and the cross-harness distribution machinery (v3.0.0). Phase 6 reads the calibration corpus — that read is treated as a Phase-6 input; the writing/compounding loop is not evaluated.

Method. ADE was re-scored from its actual v3 generated tree — every in-scope SKILL.md.j2, the worker subagent definitions (scout, synthesizer, spec-verifier, plan-reviewer, test-writer, implementer, code-reviewer, security-reviewer), and the deterministic hooks (block-mixed-commit, check-leftover-stub, check-escalation-paths) — not its prose claims. The field half leans on the 2026-06 17-system re-benchmark, whose per-dimension ratings were already adversarially verified against the real repos; this study narrows that corpus to the dev-pipeline dimensions and adds four targeted re-verification agents on the questions the narrowed lens needs fresh depth on (plan-soundness norms, design-stub/scaffold practice, bounded-repair + live-verify best practice, research-phase rigor frontier). Each agent was instructed to adversarially refute its own conclusion before settling.

The five lenses applied to every phase: (1) Strengths — leading-class behavior, evidence-backed to the skill/agent/hook that delivers it; (2) Weaknesses — weaker-than-field, brittle, or under-specified; (3) Gaps — capabilities the field has that ADE has no step for; (4) Process-rigor — isolation, determinism, circuit breakers, fail-safe behavior; (5) Field-benchmark — who does it better/differently and what ADE would adopt.

The shape of the verdict

ADE's pipeline is strongest at the front (0–1) and the TDD core (3–4), and thins out at the validation seams: the plan is only independently checked at the top tier, the design stub is self-validated, the repair loop is bluntly capped, and the final acceptance proof is test-coverage rather than running-system evidence. Every weakness is an under-applied version of a discipline ADE already owns — blind review, circuit breakers, runtime checks — not a missing concept. That makes the improvements cheap and the strengths durable.

02Per-phase deep analysis

Phase 0Intent + Route  leader

Mechanism. Extracts a structured intent (type / goal / acceptance criteria / affected areas / S-M-L scope) to .ade/tasks/<id>/intent.md, gating every later phase. Each acceptance criterion must be expressible as an automated test to count as in-loop; inherently visual/perceptual criteria are tagged (manual) and explicitly verified by a human outside the loop — "the pipeline guarantees exactly what the tests guarantee; it does not pretend a shallow render-test stands in for human review." The closing 0d Route sub-step assigns a tier — trivial / standard / architecture — that masks which later phases run. Routing is forced-escalation-first and deterministic: it reads .ade/ade-routing.json, and any affected-area or keyword match against an escalation glob floors the tier (and can never be overridden downward); a missing/unparseable config is treated as ≥ standard.

StrengthTrue phase-masking blast-radius routing with a deterministic forced-escalation floor that the check-escalation-paths commit hook re-enforces against the real diff at ship time — so a Phase-0 mis-route (no diff yet) is still caught later. The automatable-or-(manual) discipline on acceptance criteria is a rare honesty about what the pipeline can and cannot prove. Leader-class, matching gstack/ECC and ahead of the field's many informational "size labels."
WeaknessWithin the non-forced band, the trivial-vs-standard split is pure LLM size-judgment (no determinism). Routing accuracy depends on the user naming security/schema/public-API impact in Affected Areas — the skill says so explicitly. No NFR/capacity dimension is captured at intent.
GapNo incident-intake entry point (a production postmortem as a pipeline trigger) — though that is largely outside the dev-pipeline scope.
Process-rigorFail-safe by construction: unparseable config ⇒ conservative ≥standard; forced floor is irreversible downward; architecture or any forced floor requires explicit user confirmation. Strong.
FieldLeader. Microsoft CAF names blast-radius (not apparent complexity) as the primary mandate for multi-agent ceremony; ADE's deterministic floor + hook backstop is the cleanest realization in the set.

Phase 1Research (R1–R5)  leader — field-best

Mechanism. Five sub-steps producing three durable artifacts (a permanent spec, additive CONTEXT.md glossary, immutable ADRs). R2.1: parallel scout subagents with iterative retrieval (DISPATCH→EVALUATE→REFINE→LOOP, max 3 cycles) governed by an explicit stop criterion (≥3 findings at relevance ≥0.8, no critical coverage gaps, no terminology mismatch), refining vocabulary between cycles and grepping docs/learnings/ for prior discoveries. R2.2: orchestrator confidence check gates conditional R2.3 web research (Tier-0 tools by default). R3: a single-writer synthesizer drafts the spec; the orchestrator interviews the user against a 10-category ambiguity taxonomy (one question at a time, multi-choice with one recommended + one alternative, hard cap 5 questions, spec updated atomically after each answer). R4: the vendored grill-with-docs skill sharpens domain terms into the glossary + ADRs. R5: factor+revise Chain-of-Verification — extract 8–15 claims, dispatch one spec-verifier per claim in parallel, each structurally forbidden the spec text, answering from project code/docs alone; the synthesizer (Role B) then revises the spec against material findings and "never silently softens the spec to make findings go away."

StrengthThe single most rigorous recon-and-verify pipeline in the field. The defining property — the spec-verifier is the only verifier in the surveyed set that is blind to the artifact it judges in the spec direction — correctly operationalizes both the Chain-of-Verification factored variant[1] and the result that LLMs cannot reliably self-correct their own reasoning[2]. No competitor pairs all three of: iterative-retrieval scouts with a stop criterion, vendored grill-with-docs domain modeling, and factor+revise CoVe with a structurally blind verifier. The triple-durable artifact (spec + glossary + ADR chain) survives /clear and reloads into fresh windows.
WeaknessScout findings carry citations but no evidence-strength grading. The 5-question interview cap is reasonable but rigid. The NFR/capacity category exists in the taxonomy (#4) but the interview is not forced to extract a falsifiable, numeric target — "fast" can survive as a criterion.
GapThe 10-category taxonomy has no security-design / threat-surface category and no privacy/data-classification category — so design-time security and PII never enter the spec by construction.
Process-rigorBest-in-study context isolation: scouts and verifiers run in fresh windows returning condensed findings; the verifier's spec-blindness is a structural guarantee, not a prompt nicety (if the spec leaks into a verifier's prompt it self-flags as compromised). The R2.1 loop is hard-capped at 3 cycles and escalates rather than proceeding on thin research.
FieldLeader. The strongest competitor idea ADE lacks is gsd's provenance tags (VERIFIED / CITED / ASSUMED) on every research finding, with ASSUMED forcing user confirmation before a claim becomes a locked decision. gsd's goal-backward verification and BMAD's "Blind Hunter" are strong but point at code, not the spec — so ADE's independence guarantee remains the strongest in the field.

Phase 2Plan  strong soundness gap

Mechanism. Writes a 6-section plan.md (context, dependency-ordered task list / DAG, files-to-change table, dependencies, test strategy, risk areas) with a documentation-row rule (any new route/table/service/feature must add a row for the affected doc file — "documentation is a deliverable, not an afterthought"). A self-check Plan Gate verifies all sections present, dependency-ordered, every acceptance criterion covered. An adversarial blind plan-reviewer — fresh context, not given the planning reasoning, sees only spec + plan, tries to refute (hallucinated refs, weak acceptance criteria, uncovered criteria, scope creep, <2 edge cases, missing ADR), emits APPROVE/REJECT, max 2 iterations then escalate — runs only for the architecture tier.

StrengthA durable, dependency-DAG plan with the doc-as-deliverable rule, and — for high-blast-radius work — a genuinely adversarial, refusal-capable blind reviewer that is structurally denied the planning rationale. That review, where it runs, is field-class.
WeaknessThe median standard change gets no independent plan check at all — only the planner's self-authored Plan Gate checklist, which is exactly the "grade your own homework" failure mode blind review exists to catch. Four mature spec-driven systems (gsd, BMAD, Spec Kit, ECC) apply some independent plan validation to every change; ADE is the only one that drops it to zero below the top tier. gsd is the sharp counter-example — same Claude-Code substrate, yet it runs goal-backward gsd-plan-checker on all plans with stall detection, proving all-tier plan validation is operationally affordable.
Process-rigorWhere it runs, the loop is bounded (max 2 → escalate) and the reviewer is isolated. The gap is coverage, not rigor: the control's existence drops to zero for the common case, not just its severity.
FieldBehind on plan-validation universality. Steel-manned counter (CAF blast-radius right-sizing) rejected: CAF scales a control's severity, not its existence to zero — its own model keeps an independent observation layer at every tier. Best fix: a lightweight fresh-context coverage-matrix check on the standard tier (every acceptance criterion → task, à la BMAD check-implementation-readiness / Spec Kit analyze), reserving full refutation for architecture.

Phase 3Design-Check  leader (executable gate) no stub reviewer

Mechanism. Before any real code, a subagent in a dedicated git worktree (ade/<task-id>) creates stubs: full type/data definitions and function signatures with loud-failing bodies (NotImplementedError / "Not implemented" / "TODO: implement"), entrypoint/component/accessor shells — no business logic, SQL, API calls, or tests. Stubs are validated against the plan's file table: coverage (every CREATE file stubbed), type consistency (shared contracts flow to dependents), a build check on the foundation module (shared contracts must compile; dependents may fail loudly), and an import / no-circular check. Max 2 iterations then escalate. The check-leftover-stub commit hook guarantees a placeholder marker can never ship as real code. Skipped for the trivial tier.

StrengthThis is "Spec Kit's design phase made executable." Where Spec Kit only doc-checks its contracts/, ADE adds a real compile + import gate — the differentiating signal. Stubbing surfaces cross-module contract/type mismatch and circular-import problems before expensive parallel TDD, which the plan's prose file-table and TDD's per-unit RED step structurally cannot (a failing test can't distinguish "not implemented yet" from "contract doesn't compile"). The hook-guaranteed no-ship of placeholders appears to be an ADE original.
WeaknessNo independent reviewer of the stubs — the same agent creates and self-validates them, so a wrong-but-compiling contract passes the gate. The 2-iteration loop is shallow. There is also mild tension with strict TDD orthodoxy (tests, not stubs, should drive the interface), defensible here only because author-separation keeps the test-writer in charge of behavior while stubs fix only the module boundary.
Process-rigorWorktree isolation from the main tree; deterministic hook backstop on placeholders; bounded loop with escalation. The missing piece is a blind check — ADE already owns the pattern (the Phase-1 spec-verifier that never sees the spec).
FieldLeading on the executable gate, mildly over-built without a reviewer. Most systems have no skeleton phase (gsd, Superpowers go straight to TDD); ECC's scaffold runs a working slice with an optional adversarial GAN reviewer. Best fix: add a blind stub-reviewer subagent (reuse the spec-verifier isolation pattern on the contracts); keep the executable gate as the differentiator.

Phase 4Implement  leader — field-best

Mechanism. Author-separated TDD inside the worktree. 4a: the test-writer subagent writes failing tests only (test files only, never source), maps each automatable Phase-0 criterion to ≥1 test, confirms the suite is RED for the right reason (assertion failures, not import errors), and commits a test-only commit. 4b: the implementer subagent(s) — dispatched without the test-writer's reasoning, seeing only the spec, the failing tests on disk, and the stubs — write the minimum code to go GREEN, never touching test files, leaving no stub markers, committing an implementation-only commit. The block-mixed-commit hook rejects any commit mixing tests with implementation with a live EXIT=2 (bypass only via an explicit [test-refactor] marker). Disjoint-file parallel implementers are allowed; no two agents may edit the same file. Build/test run through the stack-agnostic .ade/ade-stack.md commands.

StrengthThe only system in the field that makes author-separated TDD a structural guarantee via a live commit-blocking hook, not advice — turning generator≠verifier from a convention into enforcement Anthropic explicitly recommends. The implementer is denied the test author's reasoning, so the tests are an uncontaminated contract. Stack-agnostic by construction (G5).
WeaknessResidual G1 doc defect: the Implementation Checklist (ade-implement line 103) still reads "Write unit tests alongside the implementation," directly contradicting the author-separation invariant in the same file ("Must NOT create or edit test files"). The hook still blocks a mixed commit, so enforcement holds, but the prose can mislead the implementer. A one-line fix.
Process-rigorHardest isolation in the set: separate authors, separate commits, deterministic EXIT=2 enforcement, hard file-ownership rule for parallel agents, scope-drift threshold (>2× the plan's file table ⇒ stop and re-scope). Excellent fail-safe posture.
FieldLeader. LeRisque hook-enforces a 4-way split and sdlc-skills/case do author separation, but only ADE ships the live block-mixed-commit gate. Protect this — it is the pipeline's signature.

Phase 5Quality-Gate  strong

Mechanism. A strict ordered sequence in the worktree — lint → format → build → test — each step gating the next, with a documented pre-existing-vs-newly-introduced triage (pre-existing warnings may stay; new errors must be fixed; a step that is none for the stack is skipped). On failure, a fixer subagent receives the exact errors + files, and the full sequence is re-run (not just the failing step, because fixes regress). Maximum 3 fixer attempts, then a circuit breaker escalates with all three failure rounds summarized and a root-cause pattern — "Do NOT silently retry beyond the limit."

StrengthA clean deterministic gate with an explicit, well-articulated circuit breaker and a full-sequence re-run that catches fix-induced regressions. The pre-existing-vs-new triage is more disciplined than most. Stack-agnostic via .ade/ade-stack.md.
WeaknessThe bare integer cap (max 3) lags the leaders' stall / no-progress detection: case fingerprints each failure and aborts when two cycles match; gsd requires the issue count to strictly decrease and bails on a non-decreasing round. A fixed cap cannot distinguish "making progress, needs a third try" from "stuck on the same error, wasting attempts 2 and 3."
GapNo runtime/live check lives here either — the gate proves the code builds and the tests pass, never that the wired-together system runs (see Phase 6 / G6).
Process-rigorBounded, fail-loud, escalation-on-exhaustion — field-normal and sound. The cheap upgrade is a recurring-error fingerprint to bail before the cap.
FieldStrong. Max-3-then-escalate is squarely field-normal (case=2, oh-my-claudecode/gsd/Superpowers=3). Best fix: add a no-progress fingerprint à la case/gsd.

Phase 6Review  strong G6 + single-model

Mechanism. Reviews the full main...ade/<task-id> diff. Reads docs/review-calibration.md fresh first — the compounded list of finding-classes that recur in this project, most-frequent first — and prioritizes the diff against the top classes. Preferred mechanism dispatches the pr-review-toolkit fan (code / silent-failure / test / type / comment); the documented fallback launches three parallel Sonnet lenses (Logic, Conventions, Security) plus a Test-adequacy lens that hunts tautologies, all-mocks, and missing edge cases. A four-level severity taxonomy (Critical / Important / Suggestion / Positive) gates the review-fix cycle (max 3, escalate if findings keep appearing). The review output is persisted to review.md for the (out-of-scope) compound loop.

StrengthA multi-lens, fresh-context review that reads a compounded calibration corpus to prioritize this codebase's recurring finding-classes — a feedback signal few systems wire into the gate. The Test-adequacy lens is unusually rigorous (tautology / all-mocks / criterion-coverage), treating tests as first-class review targets.
Weakness / Gap — G6Live verification was removed from the pipeline. The skill states verbatim: "Because live verification has been removed from the pipeline, this gate is the in-loop acceptance check — it replaces live evidence." The Acceptance-Coverage Gate requires every automatable criterion to have a meaningful covering test (no tautology/all-mocks) — but acceptance proof is now test coverage, never running the app / curling the endpoint / capturing output. ADE is alone among strong systems with zero runtime evidence.
Weakness — model diversityThe review fan is single-model (code-reviewer and security-reviewer are both model: sonnet). gstack and compound-engineering fan across model families for decorrelated blind spots; ADE does not.
Process-rigorFresh-context lenses, bounded review-fix cycle, persisted output. The G6 gate is internally honest (it openly says it replaces live evidence) — the issue is the substitution itself, not a hidden one.
FieldStrong, behind on live-verify. Anthropic's best-practice is explicit[3]: specs should "end with an end-to-end verification step that proves the feature works," and "show evidence rather than asserting success." Only case enforces live-runtime as a true agent-driven hard gate — alongside coverage — precisely because mocked tests pass while the wired system 500s.
G6 — why it regressed, and why the fix is cheap

The removal was deliberate, not accidental: commit c07199c ("remove live-verify phases and renumber tail to 0-9 (G5c)") deleted 07-verify.md.j2 and qa-verify-bug.md.j2 as part of G5 — the stack-de-hardcoding / language-agnostic implementer work. Live verification was stack-specific (you must know how to run and curl the app), so it was sacrificed to win stack-agnosticism. That diagnosis is also the fix: restore a per-criterion live-evidence sub-step driven through the same .ade/ade-stack.md command abstraction Phase 5 already uses for build/test — adding a run/serve command — so ADE regains running-system proof without re-hardcoding the stack. Steel-manned defense (tests are repeatable evidence; a one-shot curl rots immediately; Anthropic itself blesses "a test suite" as a valid check) holds for the durability axis but not the integration-seam axis: this is a complement gap, not a substitute gap.

05A · Confirmed strengths to protect

Ranked by how hard they are to replicate and how central they are to the inner loop. These are evidence-backed to a specific skill/agent/hook and survived adversarial re-verification — guard them in any refactor.

1 · Spec-blind Chain-of-Verification

Phase 1 / R5 · spec-verifier
Why it leadsThe only verifier in the field blind to the artifact it judges in the spec direction. Correctly operationalizes CoVe[1] + the no-self-correction result[2]. No competitor pairs iterative-retrieval scouts + grill-with-docs + factor+revise CoVe.

2 · Hook-enforced author-separated TDD

Phase 4 · block-mixed-commit (EXIT=2)
Why it leadsThe only system that makes generator≠verifier a structural commit-time guarantee rather than advice. Anthropic explicitly recommends author-separated TDD; ADE alone enforces it.

3 · Blast-radius phase-masking routing

Phase 0 / 0d · check-escalation-paths
Why it leadsA deterministic forced-escalation floor that masks which phases run and is re-enforced against the real diff at ship time. Realizes Microsoft CAF's primary multi-agent mandate more cleanly than the field.

4 · Executable design-contract gate

Phase 3 · stub build/import check
Why it leads"Spec Kit's design phase made executable" — a real compile + import gate that catches cross-module contract/circular-import faults before expensive parallel TDD, hook-guaranteed against shipping placeholders.

5 · Triple-durable spec artifact

Phase 1 · spec + CONTEXT.md + ADRs
Why it leadsA permanent spec, an additive glossary, and an immutable ADR chain that survive /clear and reload into fresh windows — the durable source of truth the field's best also keep, with the fullest triple.

6 · Conservative, bounded control flow

All phases · circuit breakers + fail-safe defaults
Why it leadsEvery iterative loop is hard-capped and escalates; unparseable config defaults to ≥standard; forced floors are irreversible downward. A genuinely fail-safe posture.
