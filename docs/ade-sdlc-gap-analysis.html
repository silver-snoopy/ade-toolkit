ADE vs. the Field

A compatibility & gap analysis of the ADE toolkit's 10-phase agentic SDLC against nine other Claude-Code-era development systems — focused on the development core: the internal steps between "approved spec" and "merged PR", and on how each system organizes its agents.

Systems compared  9 Primary sources  repos + ADRs + skill files Research agents  19 Verification  3-vote adversarial Date  2026-06-19
Bottom line

ADE is already in the top tier on verification rigor — its blind spec-verifier (Chain-of-Verification, factor+revise) and its research phase (iterative retrieval → grill → CoVe) are matched only by LeRisque among the ten systems. But on the dev core it carries five structural gaps that the field has converged away from: (1) no author-separation in implementation — ADE writes code stub-first, where the field now mandates test-writer ≠ implementer; (2) no deterministic hook layer — ADE spends agent tokens on checks competitors absorb with greppable hooks; (3) a weak "compound" step — ADE's retro is ephemeral while the field codifies every task into reusable knowledge; (4) no blast-radius routing — ADE runs the full heavyweight flow for a one-line change; and (5) a portability claim its dev phases don't honor — Phases 3–7 hardcode a JS/TS monorepo.

00Method & corpus

The study compares ADE (read directly from this repository's phase skills and architecture doc) and LeRisque (your own private PetroczyP/LeRisque repo, whose .claude/skills/sdlc + ADR-0009 you flagged) against the seven repositories in your ai-sdlc GitHub stars list. Each starred repo was investigated as a primary source: a dedicated agent read the README, file tree, and the actual agent/skill/command files via authenticated gh. Five web-research agents covered the cross-cutting concepts (compound engineering, spec-driven development, role-vs-skill architectures, agentic-SDLC patterns, code-review/verification). Every architecture classification was then re-checked by an independent adversarial verifier instructed to refute it — all nine held, with only minor count/path corrections.

03Internal-step deep dive

The four stages where the field has converged on a specific technique that ADE implements differently.

07 · Implementation discipline — TDD with author separation

This is the single sharpest divergence. Seven of ten systems make implementation test-first, and the strongest ones make it author-separated: the agent that writes the failing test is structurally distinct (fresh context) from the agent that writes the code to green.

  • LeRisque splits Stage 2 into four separate sub-agent invocations — test-writer → test-quality-reviewer → implementer (fresh context) → optional refactor — and a pre-commit hook structurally blocks mixed test+impl commits. Its ADR cites TDD-Bench Verified (best LLM fail-to-pass only 23.6%) and Self-Correction Bench (same-agent plan+review fails 64.5%) as the reason.[L,1,2]
  • case writes a failing test then makes it pass, AST-grep-gates the commit, and squashes; ECC drives every task through a tdd-guide agent with an ≥80% coverage gate; sdlc-skills/octobots bake "write failing tests (red) first" into the 8-step implement skill; gsd enforces a RED-commit before implementation under --tdd.
  • ADE is the outlier: Phase 3 generates stubs (signatures that throw), Phase 4 fills them in and "write unit tests alongside the implementation." Tests and implementation are authored by the same subagent, in the same pass — exactly the configuration the research flags as the dominant silent-failure mode (the model rewrites the test to match the code).
Gap G1

ADE's stub-first + same-agent-tests approach is the riskiest implementation pattern in the corpus. Author separation (test-writer ≠ implementer, fresh context, enforced by a commit hook) is the field's load-bearing invariant and ADE lacks it.

08 · The static gate — hooks vs. an agent

Cheap deterministic checks (lint, format, build, type-check, "no silent catch", "no stub left behind", file-size budget) are increasingly pushed out of the agent loop into continuous hooks.

  • LeRisque runs a "Continuous Layer" of greppable Python hooks (check-silent-catch.py, check-stub-patterns.py, check-non-null-assertion.py, check-file-budget.py…) that fire on every tool-use — no agent tokens, no model variance. case ships ast-rules/ AST-grep rules enforced pre-commit. ECC codifies its greppable ANTIPATTERNS as hooks.
  • ADE runs lint/format/build/test through a Haiku test-runner subagent (Phase 5) with a 3-iteration fixer loop. It works, but it spends model tokens on deterministic checks and inherits LLM non-determinism on a step that should be a hard gate. The research is explicit: "defense-in-depth should include at least one deterministic enforcement layer whose policy evaluation does not depend on LLM reasoning."[5]
Gap G2

ADE has no deterministic hook layer. The mechanical, greppable subset of its quality gate and review (silent-catch, leftover-stub, file-size, format) belongs in PreToolUse/PostToolUse hooks, freeing the review agents to do semantic work only.

09 · Review fan — how many reviewers, and how blind?

Two findings dominate. (a) Generator≠verifier: the reviewer must run in a fresh context that never saw the author's reasoning (anchoring/agreement bias otherwise inflates approval by up to 25pp[6]). (b) ~2 reviewers is the empirical optimum — marginal gain decays past two[3], and deliberately different reviewers beat duplicates (one study: 93.4% of findings caught by exactly one of four reviewers[7]).

  • ADE already does (a) well — Phase 6's fresh-context lenses, and crucially the R5 spec-verifier that never receives the spec text. On (b) ADE runs three fixed lenses (logic/conventions/security) or pr-review-toolkit's up-to-5; defensible, but heavier than LeRisque's deliberate 2 reviewers + 1 calibrated Opus Judge.
  • gstack dispatches a 7-agent "Review Army" but gates which fire by hit-rate stats; compound-engineering runs 4 always-on + ~9 conditional personas with a JSON findings schema + dedup; LeRisque's calibrated Judge targets exactly the ~20 finding-classes its post-PR bots historically raised.
ADE strength

ADE's spec-blind verifier and CoVe factor+revise are ahead of the field here — only LeRisque's calibrated Judge is comparable. This is ADE's signature advantage; don't dilute it.

12 · The compound step — does the task improve the next one?

The biggest conceptual idea in the corpus is "compounding": each completed task must deposit durable, reloadable knowledge so the next task is cheaper. compound-engineering is built entirely around it (ce-compound writes docs/solutions/ + seeds CONCEPTS.md); case's retrospective appends learnings and stages harness amendments; ECC has /learn → auto-skill extraction; gstack has /learn + GBrain; LeRisque feeds every >10-comment PR back into the Judge's calibration corpus.

  • ADE has two partial pieces: CONTEXT.md (additive glossary, via grill-with-docs) and ADRs — genuinely strong for terminology/decisions. But Phase 10 retro emits retro.json that is ephemeral and per-task; nothing mines task learnings into reusable skills or a solutions corpus, and no metric feeds back to tune the gates.
Gap G3

ADE's retro doesn't compound. The CONTEXT.md + ADR machinery is the right substrate; it needs a durable solutions/learnings sink and a feedback metric (à la LeRisque's SLI → calibration) so the pipeline self-improves.

04The architecture question: role vs language vs skill vs phase

You asked specifically about role-based vs language-based agents. The data says the binary is the wrong frame — the field has split into four organizing axes, and almost every mature system mixes them. Here is each axis, who uses it as their primary organizer, and what 2025–26 research says about it.

Role-based

agents = job titles / personas
Named human roles: CEO, Architect, QA Lead, Security Officer, Reviewer. The "virtual team" metaphor.
Primary ingstack (23 personas), case (7 fixed roles), LeRisque (8 roles), sdlc-skills/octobots (named characters w/ SOUL.md)
StrengthLegible to humans; clean "Does-Not-Do" boundaries; maps to org separation-of-duties
RiskStatic roles can't adapt mid-task; persona ≠ capability; coordination overhead

Language-based

agents = programming languages
Specialists per stack: python-dev, react-reviewer, go-build-resolver, swift-ios-reviewer.
Primary inNobody, alone. Appears as a thin slice: ECC (lang reviewers + build-resolvers), sdlc-skills/octobots (lang devs), ADE (backend/frontend coders)
StrengthStack-idiomatic conventions; targeted build-error recovery
RiskCombinatorial explosion; mostly redundant with good context + skills

Skill-based

agents = composable capabilities
Behavior modules loaded on demand: tdd, code-review, plan-feature, deep-research. Personas become emergent.
Primary incompound-engineering, ECC (271 skills), sdlc-skills (skills attached to roles), gsd (namespace meta-skills)
StrengthThe 2026 consensus unit: "a skill changes behavior, a subagent protects context, an MCP adds capability"[4]
RiskDiscovery/routing cost at scale (gsd solved via 2-stage namespace routing)

Phase-based

agents = SDLC stages
Single-purpose workers named by function: planner, executor, verifier, plan-checker.
Primary ingsd (34 phase-function agents), case (roles map 1:1 to phases), ADE (scout/synthesizer/spec-verifier)
StrengthMaps cleanly to the pipeline; each agent has one job + one artifact; easy to gate
RiskCan proliferate; needs an orchestrator to sequence
The verified consensus

Pure role-based design is over. Cognition ("Don't Build Multi-Agents") and Microsoft's framework both argue a single agent with persona-switching satisfies role behavior without orchestration cost; you escalate to multiple agents only for context-isolation, hard security boundaries, or measured single-agent limits.[4,8] The decisive technical fact is read/write asymmetry: read-heavy work (research, review, security scan) parallelizes across isolated subagents and wins; write-heavy work (editing code) should stay single-threaded because parallel writers make conflicting implicit decisions.[4] Empirically, role specialization gives task-dependent, often marginal returns on SWE benchmarks — reasoning quality, tool integration, and context engineering matter more than agent count.[9]

Where ADE sits — and what it implies

ADE is fundamentally phase-based (its subagents are pipeline functions) with a language-based slice (backend-coder / frontend-coder) and a skill-based seam (vendored grill-with-docs, referenced pr-review-toolkit). It uses no human-persona roles at all. That is, by the 2026 consensus, the correct and modern choice — ADE skipped the role-based fashion that gstack/case/LeRisque lean on, and landed on the phase+skill model the research endorses.

Implication for ADE

Don't add CEO/QA personas — that would be moving backward. The growth move is the opposite: lean harder into skill-based composition (so behavior is reusable across phases) and collapse the language slice — backend-coder/frontend-coder are a portability liability (they bake in a JS/TS monorepo) and the research says a single coder + good context + a TDD skill outperforms language-named agents. Replace them with one language-agnostic implementer driven by a TDD skill.

07Gap analysis — ADE's five structural gaps

Ordered by leverage (impact on output quality × distance from current design).

G1 · Implementation has no author separation highest leverage

ADE's stub-first → same-agent-implements-and-tests is the field's documented #1 silent-failure mode. The fix is well-trodden: split Phase 4 into a test-writer sub-agent (writes failing tests against the spec's acceptance criteria, commits them alone) and a fresh-context implementer (writes code to green, forbidden from editing the tests), with a pre-commit hook that blocks mixed test+impl commits. LeRisque's ADR-0009 is a ready-made blueprint you already own.

G2 · No deterministic enforcement layer

ADE routes mechanical checks through a Haiku agent. Move the greppable subset (format, leftover-stub detection, silent-catch, file-size budget, "no // TODO: implement") into Claude-Code PreToolUse/PostToolUse hooks. This makes the gate deterministic, frees the Phase 5/6 agents for semantic work, and removes a source of model-variance from a step that should be a hard wall.

G3 · The retro doesn't compound

ADE already persists terminology (CONTEXT.md) and decisions (ADRs) — better than most. What's missing is a solutions/learnings sink (a per-task durable doc the next task's research phase reads) and a feedback metric. Borrow LeRisque's SLI idea: count post-PR review-bot comments (or Phase 6 findings) and feed recurring classes back into the review prompts. That turns Phase 10 from a dead-end JSON into the engine that makes Phase 1 cheaper next time.

G4 · No blast-radius routing

ADE's architecture doc explicitly states the S/M/L scope estimate "does not route Phase 1" and the full flow runs regardless. Eight of ten competitors classify change size and mask which phases run (case's tiny-profile, ECC's tier classifier, LeRisque's trivial/standard/architecture routing, gsd's --mvp). A one-line doc fix shouldn't pay for stub-design + live Playwright verification. Add a router after Phase 0 that can skip Phases 3/6/7 for trivial changes — with security/public-API changes forced to at least standard.

G5 · The portability claim vs. the JS/TS-coupled dev phases

The architecture doc sells ADE as stack-agnostic, but Phases 3–7 hardcode @vitals/shared, npm run build -w, packages/backend, Playwright, and a "shared → backend → frontend" build order. Every truly portable competitor (sdlc-skills' command-translation tables, ECC's 12 ecosystems, gsd's multi-runtime installer) externalizes stack commands into a detected/config file. ADE's own detect.py already identifies the stack — wire that into the phase prompts instead of hardcoding the example project's conventions.

Two deliberate non-gaps

Cross-harness (Claude-Code-only) and multi-instance/messenger orchestration (octobots-style) are legitimate scope choices, not deficiencies — ADE is a single-session Claude-Code scaffolder by design. And ADE's Claude-only review (vs gstack/ECC's Codex/Gemini cross-model fan) is a genuine trade-off: cross-model diversity catches more (93.4% disjoint findings[7]), but LeRisque deliberately chose calibration over diversity. Treat cross-model review as optional, not a gap.
